# 複雑なシステム：管理画面、ログイン、ファイルアップロード、データベース

適用範囲：ログイン、管理画面、ファイルアップロード、データベースのいずれかがあるシステム、または複数人で共用するシステム。

> 標記の説明：〔法〕法律に明文の規定があるもの。〔府〕行政院または台北市政府の指針・規定。〔推奨〕本規範が推奨するやり方。法令の原文と出典は `legal-sources.md` を参照。

管理画面、ログイン、ファイルアップロード、データベースがあるシステムは、リスクも使われ方も単純なウェブページとは異なる。`web-ui.md`、`privacy.md`、`security.md` の規定に加えて、本書にも従う。

### 一、着手前に説明する：この種のシステムには情報部門の関与が必要である

システムに次のいずれか一つでもある場合は、着手前に担当職員に**必ず**伝え、本番稼働前に機関の情報部門の関与を求めること。自分で作り終えてそのままインターネットに公開してはならない。〔府〕「臺北市政府資通安全管理規定」（台北市政府情報通信セキュリティ管理規定）

- ログインが必要（アカウントとパスワード、臺北通（TaipeiPASS）、市政府のシングルサインオンなど）
- 管理画面があり、データの追加、修正、削除ができる
- 市民や職員がファイルをアップロードできる
- データをデータベースに保存し、かつ個人情報を含む
- メールや SMS を送信する、他機関のシステムと連携する

次のように説明するとよい。

> このシステムには管理画面とファイルアップロードがあり、情報通信システムに当たります。本番稼働前に、機関の情報部門による防護等級の評価と脆弱性スキャンを受け、サーバーとバックアップを手配する必要があります。先にプログラムを作ってお試しいただくことはできますが、ご自身で外部ネットワークに公開するのは控えてください。今のうちに情報部門へ連絡しておくことをお勧めします。

この種のシステムは「tech-stack.md 一」の第二級または第三級に当たる。技術を選ぶ前に、機関に既定のプラットフォームやサーバーがあるかを担当職員に尋ね、あればそれに優先して合わせる。なければ「tech-stack.md 一」に従って選び、構成を納品説明に書いて情報部門が評価できるようにする。

### 二、二種類の画面、二種類のレイアウト

同じシステムの中でも、市民向けのページと職員が使う管理画面はレイアウトを分けるものとするが、配色とコンポーネントは同じものを共用する。

| | 外部向けページ | 管理画面 |
|---|---|---|
| 利用者 | 市民。たまに使う | 職員。毎日長時間使う |
| 目標 | 一目でわかり、安心できる | すばやく探せ、すばやく直せ、誤りが起きない |
| 幅 | 約 40em の一段組み | 画面いっぱい。最大約 90em |
| ナビゲーション | ヘッダーの簡単なメニュー | 左側の機能メニュー（スマートフォンでは折りたたみ可能にする） |
| 見出し | 明朝体の大見出し、市章四色帯 | ゴシック体（`<body class="tp-admin">`）。四色帯は置かない |
| 内容 | 条文式の説明、主ボタン一つ | 表、絞り込み条件、一括操作 |
| 文字サイズ | 本文 16px 以上 | 本文 15〜16px、表は 14px まで可 |
| アクセシビリティ目標 | 機能に応じて判断（多くは AAA または AA） | 少なくとも AA |

管理画面は正式な業務画面であり、既定デザインを用い、「web-ui.md 八、使ってはいけないスタイル」の表に挙げたスタイルは使わない。管理画面のヘッダーには局・処のロゴ（見つからない場合は機関の正式名称の文字）とシステム名を置き、「管理系統」（管理システム）であることをはっきり示して、職員が外部向けサイトと混同しないようにする。

**管理画面のレイアウト**

```
┌──────────────────────────────────────────────────┐
│ 局處 Logo ＋ 〇〇管理系統          王小明（承辦人）登出 │
├────────────┬─────────────────────────────────────┤
│ 案件管理   │ 案件管理／案件列表                    │
│ 檔案管理   │ 案件列表                    [新增案件] │
│ 帳號管理   │ ┌篩選：狀態▼  日期起迄  關鍵字 [查詢]┐ │
│ 操作紀錄   │ ├────────────────────────────────┤ │
│            │ │ 表格（可排序、分頁）              │ │
│            │ └────────────────────────────────┘ │
└────────────┴─────────────────────────────────────┘
```

**スマートフォンでの管理画面のヘッダー**

スマートフォンの幅（640px 以下）では、ヘッダーは一行だけにし、局・処のロゴ（または機関の正式名称の文字）とシステム名を置く。長すぎる場合は、システム名を短くするか、ロゴの下に折り返してよい。利用者名、ログアウト、機能メニューはすべて「選單」（メニュー）ボタンの中に収め（開閉は `aria-expanded` で示す）、ヘッダーに詰め込まない。

**管理画面のフッター**

内部の管理画面のフッターは `<main>` の外に置き、次の項目だけを置けばよい。

1. 機関の正式名称
2. システムに関する問合せ窓口（部署、内線番号またはメールアドレス）
3. システムのバージョンまたは最終更新日
4. アクセシビリティ宣言（リンク）
5. システムが個人情報を扱う場合は「資料保護說明」（データ保護に関する説明）（リンク）

外部向けページのフッターに求められる住所、データ公開宣言、ポータルサイトへのリンクは、管理画面では省略してよい。「資料保護說明」は職員向けに書くもので、システムにどのような個人情報があるか、誰が見られるか、どれくらいの期間保存するか、アクセスは記録されること、漏えいした場合に誰へ報告するかを説明する。外部向けプライバシーポリシーの六項目の告知をそのまま写す必要はない。

**管理画面のログインページ**

ログイン前のページ（ログイン、パスワードを忘れた場合、初回ログイン時のパスワード変更）には左側メニューを置かず、一段組みの中央寄せレイアウト（幅約 28em）とする。ヘッダーには局・処のロゴとシステム名を置いて「管理系統」と示し、見出しはゴシック体とし、四色帯は置かない。

**管理画面のコンポーネントの規定**

- **表**：`<caption>`、列見出し、ページ送り、1 ページあたりの件数を備える。並べ替え可能な列見出しはボタンにし、`aria-sort` で現在の並び順を示す。データが多い場合はサーバー側でページ分割し、一度にすべてを読み込まない。
- **絞り込み**：絞り込み条件は表の上に置き、「查詢」（検索）を押したときに適用する。一文字入力するたびに検索し直さない。
- **確認が必要な操作**：次の操作は、まず確認ダイアログを表示し、どのデータに何をするか、どのような結果になるかをはっきり書かなければならない。市民の権益に影響する決定は、担当職員の確認を経て初めて効力を生じるものとし、プログラムが自動で決定してはならない。〔府〕市政府の AI 作業指針の絶対禁止事項。〔推奨〕確認ダイアログのやり方
  - 市民の権益に影響する決定：承認、却下、差戻し、採用、補欠への登録、書類補正の通知。
  - 市民に通知する操作：メール送信、SMS 送信、公告。
  - 元に戻せない操作：削除、一括修正、インポートによる上書き。

  書き方の例：「確定退回案件 1150012（王○明，國畫山水）嗎？退件後將以簡訊通知申請人。」（案件 1150012（王○明、国画山水）を差し戻してよろしいですか。差戻し後、SMS で申請者に通知します。）「停用」（停止）や「移到回收區」（ごみ箱へ移動）で済むなら、実際には削除しない。
- **理由欄**：市民に不利な決定（却下、差戻し、書類補正の通知）は、理由を記入しなければ送信できないようにし、欄の説明に「這段文字會通知申請人」（この文章は申請者に通知されます）と注意書きを入れる。承認、採用のような有利な決定では、担当職員が任意で備考を記入できるようにしてよい。
- **一括操作**：まずチェックを入れ、次に操作を選び、実行前に「將對 12 筆資料執行停用」（12 件のデータを停止します）と表示する。
- **状態**：文字と色で示し（「已結案」（完結）、「處理中」（処理中）、「退件」（差戻し））、色の点だけで示してはならない。
- **ダイアログ**：ネイティブの `<dialog>` 要素を使う。開いたときはフォーカスをダイアログ内に移す。理由の記入が必要なものは理由欄に、確認だけのものは「取消」（キャンセル）にフォーカスを置き、Enter を押しただけで誤って送信されないようにする。Esc で閉じられるようにし、閉じた後はフォーカスを元のボタンに戻す。ボタンは「取消」を先、確認ボタンを後に並べ、確認ボタンの文言には操作を書く（「確定退件」（差戻しを確定）とし、「確定」とだけ書かない）。注意：ダイアログを `<form>` の中に置くと、ダイアログを閉じていても、その中の `required` が付いた欄がブラウザに検査され、フォーム全体の送信が止められてしまう。ダイアログには独立した `<form method="dialog">` または独立した送信用フォームを持たせる。確認が必要な操作は、JavaScript がない環境でも動作するようにする（例えば、先に確認ページへ移動させる）。
- **ログインのタイムアウト**：タイムアウトの 2 分前に知らせ、ボタンを一度押せば延長できるようにし、職員が入力途中のデータを失わないようにする。

### 三、ログインと権限

ログイン方式のせいで開発が滞らないようにする。臺北通や市政府のシングルサインオンのような連携は別途申請が必要で、開通するまではテストができないため、二段階に分けて扱う。

**開発・試行段階**

- まずはシステム独自のアカウントとパスワードでログインし、担当職員がすぐに試して機能を確認できるようにする。
- ログインの処理は独立したモジュールとして書き、他の機能は「今誰がログインしていて、どの役割か」をこのモジュールを通じてのみ取得する。後で別のログイン方式に替えるときも、このモジュールを直すだけで済み、システム全体に手を入れなくてよい。
- 独自のアカウントとパスワードでも、基本的な安全対策は行う。
  - パスワードは bcrypt、scrypt または Argon2 でハッシュ化して保存し、平文や復号可能な暗号化で保存してはならない。
  - 連続して誤入力した場合は一時的にロックする。機関の規定がない場合は、既定で 5 回連続の誤りで 15 分間ロックする。ロックは「アカウントと送信元 IP の組」で数えるか、試行ごとに待ち時間を延ばす方式にし、悪意のある者がわざと誤入力して他人のアカウントをロックできないようにする。
  - パスワードは 12 文字以上とし、定期的な変更は強制しないが、よくある弱いパスワード（例えば `12345678`、`password`）は拒否する。
  - 30 分間操作がなければ自動でログアウトし、タイムアウトの 2 分前に知らせ、ボタンを一度押せば延長できるようにする（本書二を参照）。
  - 以上は既定値である。機関の情報通信セキュリティ規定に別の要求がある場合は、機関の規定に従う。
  - `admin／admin` のような既定のアカウント・パスワードをハードコードしてはならない。初期の管理者アカウントは起動コマンドまたは設定ファイルで作成し、初回ログイン時にパスワード変更を強制する。

**本番稼働段階（推奨）**

- 市民のログイン：臺北通（TaipeiPASS）との連携を検討することを推奨する。
- 市政府職員のログイン：機関または市政府の既存のシングルサインオンの利用を検討することを推奨する。
- 管理者アカウントには多要素認証を加えることを推奨する。
- これらはいずれも申請と開通が必要である。納品説明で、早めに機関の情報部門または台北市政府資訊局（情報局）に相談し、開発と並行して進めるよう担当職員に注意を促す。AI が連携仕様を勝手に想定してはならない。わからない箇所は〔待確認〕（要確認）と示す。
- 最終的に連携するかどうか、どの方式を使うかは、システムの性質に応じて機関が決める。連携しない場合も、本番稼働時には「開発・試行段階」に挙げた基本的な安全要件を満たすこと。

- **権限**：
  - 少なくとも「一般承辦」（一般担当職員）と「管理者」の二つの役割を分け、最小権限の原則に従って権限を与える。
  - すべてのバックエンド API で「この人にこの操作を行う権限があるか」を検査しなければならず、フロントエンドのボタンを隠すだけでは足りない。
  - URL を公開しないことだけで管理画面を守ってはならない。
  - 担当職員が自分の業務範囲のデータだけを見られるようにする場合、照会条件はバックエンドで強制的に付加し、フロントエンドの絞り込みに任せてはならない。
- **セッション**：Cookie に `Secure`、`HttpOnly`、`SameSite=Lax` を設定する。ログアウト時にはサーバー側のセッションを無効にする。フォームの送信には CSRF 対策を施す。
  - 試行段階で、自分のパソコン上で `http://127.0.0.1` または `http://localhost` を開く場合、ブラウザは `Secure` Cookie を許可するので、通常どおりログインできる。同僚が LAN の IP（例えば `http://192.168.x.x`）から接続するとログインできないが、これは正常な安全上の動作である。便利さのために `Secure` を外してはならない。README で自分のパソコンの URL でのみ試せることを説明するか、情報部門に HTTPS 対応のテストサーバーを用意してもらう。
- **市民向けの照会機能**：市民が「番号と携帯電話番号」のような情報で照会や取消しを行う機能では、失敗回数を制限する。機関の規定がない場合は、既定で同じ送信元 IP から 15 分以内の失敗を最大 10 回とし、番号を当て推量されないようにする。

### 四、ファイルアップロード

ファイルアップロードは最もよく攻撃に使われる機能の一つであり、次の規定は**すべて**満たさなければならない。

1. **ファイル形式を制限する**：業務に必要な形式（例えば PDF、JPG、PNG）だけをホワイトリストで受け付ける。拡張子だけで判断せず、バックエンドでファイルの実際の内容（マジックナンバー）を検査する。`.exe`、`.js`、`.html`、`.svg`、`.php` など、実行できるファイルやプログラムコードを含むファイルは常に拒否する。
2. **サイズと数を制限する**：1 ファイルあたりの上限と合計の上限を設け（例えば 1 ファイル 10MB、一度に最大 5 個）、フロントエンドで案内し、バックエンドで強制する。
3. **名前を付け直す**：保存時にはシステムが生成したランダムな名前を使い、利用者がアップロードしたファイル名をそのまま使わない（元のファイル名はデータベースに別に保存する）。
4. **保存場所**：ウェブサイトのルートディレクトリの外、またはオブジェクトストレージに保存し、URL で直接開いたり実行したりできないようにする。ダウンロード時はプログラムで権限を検査してから送信し、`Content-Disposition: attachment` と正しい `Content-Type` を設定する。
5. **ウイルススキャン**：外部にアップロードを開放するシステムでは、ウイルススキャンを経てから担当職員が開くようにする。スキャンの仕組みの提供は、担当職員から情報部門に相談してもらう。
6. **個人情報**：アップロードされるファイルには身分証の写しや診断書などの個人情報がよく含まれる。保存期間を明記し、期限が来たら自動で削除する。管理画面では権限のある人にだけ表示する。
7. **画像**：市民がアップロードした画像からは EXIF 情報（撮影場所が含まれることがある）を取り除く。
8. **記録**：誰がいつどのファイルをアップロード、ダウンロード、削除したかを記録する。

アップロード欄自体もアクセシビリティを満たすこと。

- ネイティブの `<input type="file">` を使い、`<label>` と組み合わせる。
- 欄の説明に、受け付ける形式とサイズを明記する（「可上傳 PDF、JPG、PNG，單檔 10MB 以內，最多 5 個」（PDF、JPG、PNG をアップロードできます。1 ファイル 10MB 以内、最大 5 個））。
- アップロード後は選択したファイル名を一覧表示し、各ファイルの横にキーボードで操作できる「移除」（削除）ボタンを置く。
- アップロードの進行状況と結果は `role="status"` の領域に置く。
- ドラッグ＆ドロップによるアップロードを作ってもよいが、ボタンでファイルを選ぶ方法も必ず残す。

### 五、操作記録〔推奨〕

管理画面のあるシステムは操作記録を残さなければならない。問題が起きたときに、誰が、いつ、何をしたかを調べられるようにするためである。

- ログイン、ログアウト、ログイン失敗、追加、修正、削除、エクスポート、権限変更、ファイルのダウンロードを記録する。
- 各記録には、日時、アカウント、送信元 IP、操作、対象（例えば案件番号）を含める。
- 記録にはパスワードを書かず、個人情報の全体も書かない（「案件 1150012 の電話番号欄を修正した」と記録し、新しい電話番号は記録しない）。
- 一般の利用者は記録を修正・削除できないようにする。
- 保存期間は機関の規定に従う。規定がない場合は、担当職員から情報部門に相談してもらい、自分で決めない。

### 六、エクスポートと帳票

- エクスポート機能には権限管理を設け、操作記録に記録する。
- エクスポートする個人情報の項目は既定でマスクし、完全な情報が必要な場合は理由を示して承認を得る。
- CSV をエクスポートするときは、セルの先頭が `=`、`+`、`-`、`@` の内容に単一引用符を前置し、Excel で開いたときに数式として実行されないようにする。`.xlsx` をエクスポートするときは、セルに文字列型で書き込む。
- グラフには同じデータの表もあわせて示す（「accessibility.md 五」を参照）。

### 七、定員と二重送信

申込、予約、申請のような定員のあるシステムで最も問題が起きやすいのは、**定員超過**と**二重申込**である。フロントエンドで連続クリックを防ぐだけでは足りず、バックエンドで次を行わなければならない。

- 定員の確認と書込みを同じデータベーストランザクション内で完了させ、そのイベントの行をロックする（または「現在の人数が定員未満の場合にだけ 1 を加える」のような条件付き更新を使う）。多くの人が最後の一枠を同時に取り合ったときに定員を超えないようにする。
- フォームごとに使い捨てのトークンを持たせ、同じトークンで重複して送信されても 1 件だけ作成し、同じ結果ページに戻す。
- 業務ルールに応じてデータベースに一意インデックスを設ける。例えば「同じイベントには同じ携帯電話番号で一度しか申し込めない」とし、プログラムに漏れがあってもデータベースでもう一度止められるようにする。
- フォームの送信に成功したら結果ページへ転送し（Post/Redirect/Get）、利用者が再読込みしても再送信されないようにする。
- 納品前に、複数人が最後の一枠を同時に取り合う、送信ボタンを連打する、同じデータで重複して申し込む、の各場合を実際にテストする。

### 八、複数機関で共用するプラットフォーム

一つのプラットフォームを多くの局・処で共用する場合（例えば全市のイベント申込、共用の予約システム）は、次のとおりとする。

- **ヘッダーとフッター**：運用保守を担う機関（例えば資訊局）のロゴと連絡先を置き、フッターに「本網站由臺北市政府〇〇局維護」（本サイトは台北市政府〇〇局が運用保守しています）と記す。
- **各ページの内容**：各イベントやサービスのページには、主催機関と問合せ方法をはっきり書き、問題があれば誰に連絡すればよいかが市民にわかるようにする。
- **個人情報の告知**：収集機関にはそのイベントを主催する機関を書き、告知事項は主催機関が入力した内容を自動で差し込む。あわせて、サイトをどの機関が運用保守しているかを記す。主催機関と運用保守機関の間に個人情報の処理の委託関係がある場合、具体的な書き方は担当職員から機関の法制担当または個人情報窓口に確認してもらう。
- **権限**：各機関は自機関のデータだけを閲覧・管理できるようにし、照会条件はバックエンドで強制的に付加する（本書三を参照）。
- **ページ上の機関情報**：主催機関の住所や電話番号を表示する場合は、各機関の担当職員が管理画面で入力するか、AI が各機関の公式サイトから書き写して出典を示す。わからない場合は〔請填入〕（記入してください）とし、作り上げない。

### 九、データベース

- 常にパラメータ化クエリまたは ORM を使い、文字列連結で SQL を組み立ててはならない。
- データベースのアカウントにはプログラムに必要な権限だけを与え、最高権限のアカウントで接続しない。
- 個人情報の項目は必要に応じて暗号化して保存する。
- 納品説明で、本番稼働前にバックアップの仕組みを整え、実際に復元をテストするよう注意を促す。

### 十、納品時に追加して書くこと

納品説明（`delivery.md`）の「四、正式に他人に使ってもらう前に何をする必要があるか」には、一般的な項目に加えて次を挙げる。

- 情報部門の協力が必要な項目：サーバー、HTTPS、ウイルススキャン、バックアップ、脆弱性スキャン。臺北通やシングルサインオンと連携する場合は、早めの申請も必要である。
- システムで使うアカウント、役割、権限の設計。
- データの保存期間と削除方法。担当職員の確認が必要なものを示す。
- システムの起動方法と更新方法。後で引き継いで保守する人向けに書く。
