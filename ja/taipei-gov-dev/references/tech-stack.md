# 技術の選択

適用範囲：ウェブページやシステムを作る場合。データ処理ツールは `data-tools.md` を参照。

一、**要件に見合った技術を選び、必要以上のものは使わない。** 技術に制限はなく、Node.js、ビルドツール、フロントエンドフレームワーク、データベースのいずれも使ってよい。肝心なのは「要件を満たす最も簡単なやり方」を選ぶことである。簡単であるほど、担当職員が理解・修正しやすく、後任者も保守しやすい。SKILL.md の作業手順「（二）読み込み状況を報告し、判断とやり方を説明する」で、どの級を選んだかとその理由を説明する。

| 級 | 適した要件 | 推奨するやり方 |
|---|---|---|
| 第一級：静的ページ | イベントの説明、お知らせ、申請の注意事項、既存システムに送信するフォーム | HTML、CSS、少量の素の JavaScript。ツールのインストールが不要で、ブラウザで直接開けば画面が見られ、担当職員自身も文言を直せる |
| 第二級：データを保存する | オンライン申込、市民による本人データの照会、意見の受付、簡単な案件登録 | バックエンドのプログラムとデータベースを加える。バックエンドには Python（FastAPI、Flask、Django）、Node.js（Express など）、または機関が既に使っている言語（PHP、Java、.NET など）を使ってよい |
| 第三級：複雑なシステム | 管理画面、複数の役割と権限、ダッシュボード、多数のインタラクティブな画面、ファイルアップロード | バックエンドとデータベースは第二級と同じ。画面はサーバーで生成してよく（例えば Flask、Django のテンプレート）、インタラクションが多い場合に限り React、Vue などのフレームワークとビルドツールを使う。第三級だからといって必ずフロントエンドフレームワークを使うわけではない。あわせて「systems.md」に従う |

選ぶときは次の順序で考える。

1. **機関が既に持つプラットフォームと技術**：機関の情報部門が既に使っている言語、データベース、サーバーに優先して合わせる。システムが完成した後に引き継いで保守できる人がいることは、技術が新しいかどうかよりも重要である。
2. **担当職員が自分で保守できるか**：担当職員が文言の修正しかできない場合は、できるだけ第一級にとどめる。情報部門の職員の支援がある場合に、上の級へ進む。
3. **機能に本当に必要なものは何か**：市民にフォームを記入してもらうだけなら、そのためにフレームワーク一式を組む必要はない。逆に、管理画面や複数の権限があるシステムを、素の HTML で無理につぎはぎすることもしない。

二、**データベース。**

- 開発と試行の段階では、まず SQLite を使ってよい（ファイル一つが一つのデータベースで、別途インストールが不要）。担当職員がすぐに試せる。
- 本番稼働時は、機関の情報部門の計画に従い、PostgreSQL、MySQL、SQL Server などのデータベースを使う。プログラムは ORM またはデータベース抽象化層を通じてデータにアクセスし、将来データベースを替えるときに大きく書き換えずに済むようにする。
- データベース接続文字列やアカウント・パスワードは環境変数または設定ファイルに置き、ソースコードに書いてはならない。設定ファイルもバージョン管理に入れてはならない。
- その他のデータベースの規定は「systems.md 九」を参照。

三、**どの級でも守ること。** フレームワークやコンポーネントライブラリを使う場合も、本規範の見た目、用語、アクセシビリティ、情報セキュリティの規定を守る。`tp.css` の CSS 変数は React、Vue などのフレームワークでもそのまま使える。Mantine、Bootstrap のようなコンポーネントライブラリを使う場合は、配色、フォント、角丸を本規範の設定に改め、グラデーション、大きな影、アニメーションなど既定デザインで使わないスタイルを取り除く（「web-ui.md 八」）。

四、**ファイル構成（第一級の静的ページ）。** `templates/web/` からテンプレートをコピーして始める。第二級、第三級は使用するフレームワークの慣例に従って配置するが、アクセシビリティ宣言とプライバシーポリシーの二ページ（内部の管理画面では「資料保護說明」（データ保護に関する説明）に替える。「systems.md 二」を参照）と、後任者向けの README.md は備えること。

```
プロジェクトフォルダ/
├── index.html          トップページ
├── accessibility.html  アクセシビリティ宣言
├── privacy.html        プライバシー及び個人情報保護ポリシー
├── assets/
│   ├── tp.css          共通スタイル
│   ├── app.js          共通プログラム（インタラクションがなければ不要）
│   ├── logo.svg        局・処のロゴ（機関の公式サイトから取得。「web-ui.md 四」を参照）
│   └── favicon.ico
└── README.md           修正方法と本番稼働の方法の説明
```

五、**外部リソース。**

- トラッキングコード、広告コード、出所不明のプラグインを読み込んではならない。
- フォント、アイコン、ライブラリはダウンロードして自分の `assets/` フォルダに置き（自前で配信）、外部の CDN に直接つながない。
- どうしても CDN を使う場合は、バージョン番号を固定し、`integrity`（SRI）属性を付けなければならない。
- パッケージを選ぶときは、選んだバージョンに公表済みのセキュリティ脆弱性がないことを確認し、公式の最新の修正版を優先して使う。修正版が公式サイトにだけ置かれ、npm や PyPI にはないパッケージもあるので、公式の説明に従う。
- パッケージを選ぶ前に、「危害國家資通安全產品」（国家の情報通信セキュリティを害する製品）でないことを確認する。不確かな場合は、担当職員から機関の最高情報セキュリティ責任者（資安長）または情報部門に確認してもらう。

六、**言語設定。** `<html lang="zh-Hant-TW">`。英語版がある場合は英語のページを別に作り、`lang="en"` とする。
