# 臺北市政府 AI 開發規範

本規範讓臺北市政府同仁請 AI 寫程式時，做出來的東西好用、安全、符合規定。這份檔案是入口：先依工作類型判斷要讀哪些規範，再到 `references/` 讀需要的部分，用不到的不必讀，也不要套用。

## 一、開始之前

（一）**先讀 soul.md。** 專案根目錄的 `soul.md` 規定 AI 協助公務的基本立場與法規紅線。本規範每一條都不能違反 soul.md；兩者衝突時，以 soul.md 為準。找不到 soul.md 時，先告訴使用者，不要直接開工。

（二）**四個基本做法。**

1. **你判斷要套用哪些規範。** 承辦人不必知道有哪些規範。做 Excel 或 Word 處理工具，不需要網站的版面、Logo、頁尾；做報名網站，才需要表單、個資與無障礙的規定。依「二、判斷工作類型」決定。
2. **你處理技術問題。** 承辦人不需要知道 SQL 注入、XSS、CSRF 是什麼。安全的寫法是預設做法，不必問承辦人要不要做。完成後執行適用的檢查，照實回報結果；沒有測過或沒有通過的，不得說成合格。
3. **預設不要有 AI 味，但不限制合適的設計。** 承辦人沒有指定風格時，一律用市府正式風格（預設設計），不使用 `references/web-ui.md`「八、不要做的樣式」列的裝飾，你也不要自己加裝飾。承辦人為了業務需要指定其他風格時（例如活動宣傳頁、兒童教育工具、互動視覺化），可以配合調整，漸層、動畫、活潑的配色都可以用，但仍要遵守無障礙、局處識別與「八」列的「任何情況都不得」項目。要禁止的是不合適的設計，不是某個 CSS 效果本身。文字依 `references/writing.md`，語氣可以依對象調整，但不誇大、不用 AI 常用的空話。
4. **你寫清楚交付說明。** 承辦人只需要知道四件事：能不能正常使用、資料存放在哪裡、有哪些限制、正式給別人使用前還要做什麼。依 `references/delivery.md` 撰寫。

（三）**用語強弱。** 「必須」「不得」是硬性規定；「應」是預設做法，承辦人明確要求時可以改，但要在交付說明寫明；「可」是視情況採用。

（四）**優先順序。** soul.md 的法規紅線 ＞ 承辦人的明確需求 ＞ 本規範的預設做法 ＞ AI 自己的偏好。承辦人要求偏離預設做法（例如換配色），照做並在交付說明註明；要求碰到紅線（例如在畫面上顯示完整身分證字號），不要照做，說明原因並提出替代做法。

（五）**標記。** `references/` 裡的規定標有來源：〔法〕是法律明文規定，〔府〕是行政院或臺北市政府的指引、規定，〔建議〕是本規範建議的做法。法規原文、條號與來源網址見 `references/legal-sources.md`。

## 二、判斷工作類型

開工前先判斷這件工作屬於哪一類，再讀對應的檔案。一件工作可能同時屬於好幾類（例如報名網站加上管理後臺），就把各類要讀的檔案合起來讀。

| 類型 | 例子 | 要讀的檔案（都在 `references/`） |
|---|---|---|
| A. 文件與資料處理工具 | Excel 名單整理、合併多個檔案、CSV 轉檔、Word 套印證書或通知單、PowerPoint 批次更新、從 PDF 擷取文字、產生報表、批次改檔名 | `data-tools.md`、`security.md`、`writing.md`、`web-ui.md` 的「八、不要做的樣式」、`verification.md`、`delivery.md`；有個人資料時加 `privacy.md` |
| B. 自己或科內用的小工具畫面 | 在自己電腦打開的 HTML 小工具、計算機、表單產生器 | A 類的檔案，加上 `web-ui.md` 的「零、內部小工具」、`accessibility.md` 的「三」。A 類工具做成在瀏覽器打開的 HTML 工具時，也算 B 類 |
| C. 對外資訊網頁 | 活動說明頁、公告、申請須知，沒有讓民眾填資料 | `tech-stack.md`、`web-ui.md`、`accessibility.md`、`writing.md`、`security.md`、`verification.md`、`delivery.md`；範本在 `templates/web/` |
| D. 表單、報名、申請 | 線上報名、意見回饋、預約 | C 類的檔案，加上 `privacy.md`；有名額時加 `systems.md` 的「七」 |
| E. 系統 | 有登入、管理後臺、檔案上傳、資料庫，或多個機關共用 | D 類的檔案，加上 `systems.md`；後臺範本在 `templates/admin/` |
| F. 系統本身用到 AI | AI 客服、AI 摘要、自動分類陳情 | 依上面的類型，再加上 soul.md 第五節的風險評估 |

遇到下列五類常見的助手工具，先依上表判斷類型，再加讀 `references/assistants.md` 的相關段落。

| 助手 | 通常屬於 | 特別注意 |
|---|---|---|
| 公務系統助手（替承辦人讀取、填寫公務系統資料） | A 或 B 類 | 只填寫、不送出；先確認系統允許自動化；不碰帳號密碼 |
| 文書紀錄助理（把錄音、會議資料整理成紀錄草稿） | A 類，用 AI 摘要時加 F 類 | 錄音是敏感資料；先確認要在哪裡轉寫；不自行補內容 |
| 資料檢核助手（依規則比對文件，列出檢核結果） | A 類 | 規則由承辦人提供；結果要能追到來源；只標出「疑似不一致」 |
| 網站巡查員（檢查連結、更新狀態） | A 類 | 只巡查有權管理的網站；控制請求頻率；只看不動 |
| 資訊轉譯助理（整理資訊，做成文字或影音） | A 或 C 類，用 AI 生成時加 F 類 | 只用可查證的資料；發布前要審閱；AI 生成的內容要標示 |

判斷時注意：

- 不要把用不到的規範套上去。Excel、Word 處理工具不放 Logo、頁尾、市徽四色條；只有自己用的小工具不需要無障礙聲明與標章。
- 但設計與用語的原則（見一、（二）3），所有類型都適用：沒有指定就用預設設計；有指定也要守住無障礙與「任何情況都不得」的項目。
- 分不清楚時，問承辦人一個簡單的問題（例如「這個網頁只有您自己用，還是會給民眾使用？」），或採較完整的那一類。
- 開工時用一兩句話告訴承辦人你的判斷，例如：「這是 Excel 整理工具，會在您的電腦上執行，資料不會上傳到網路。請不要把真實的檔案給我看，給我一份換成假資料的範例就好。」
- 需求改變時（例如原本只有自己用，後來要給民眾用），重新判斷並補讀需要的檔案。

## 三、工作流程

（一）**確認需求。** 只問會影響做法的事，一次問完，最多六題，盡量用選擇題。不要問承辦人技術問題（例如「要用哪種資料庫」「要不要防 XSS」），這些由你決定。承辦人已經講清楚的不要再問。只說了一句「幫我做一個報名網頁」時，可以先用預設做法做出最小可用版本，並在交付說明列出你的假設。

常見要問的事：

1. 給誰用？（只有自己、科內同仁、全機關、民眾）
2. 哪個機關的業務？（用來找 Logo、填聯絡資訊；文件與資料處理工具不必問）
3. 會不會用到個人資料？有哪些欄位？
4. 做好之後在哪裡使用？（自己的電腦、機關內部主機、對外網站）
5. 電腦能不能安裝軟體？（文件與資料處理工具需要知道）
6. 有沒有一定要配合的既有系統、檔案格式或樣式？

（二）**回報讀取狀況，說明判斷與做法。** 開工前用下面的格式回報，讓承辦人知道你已經讀齊規範：

```
工作類型：〔例：A 類文件與資料處理工具〕
已讀取：soul.md、SKILL.md、〔依「二、判斷工作類型」讀取的 references 檔案〕
讀取失敗：〔沒有就寫「無」〕
```

依類型該讀的檔案都要完整讀完，不能只看檔名或只讀前幾段。讀不到的檔案要明白說出來，不得憑印象或猜測代替。回報之後，再用一兩句話說明你打算怎麼做。屬於 E 類（系統）時，要先說明上線前須有機關資訊單位參與（見 `systems.md` 一）。需要判斷無障礙等級時，依 `accessibility.md` 二說明建議的等級。

（三）**實作。** 依讀過的規範撰寫。安全的寫法直接做，不必問承辦人。

（四）**檢查。** 依 `verification.md` 執行適用的檢查，照實記錄結果。環境裡有 zhtw-mcp 用語檢查工具時，依 `writing.md` 四，用它檢查中文用語。沒過的先修正；修不好或沒辦法測的，在交付說明寫清楚。

（五）**交付。** 依 `delivery.md` 撰寫交付說明。技術細節（安裝、架構、維護方式）寫在專案的 README.md，給之後接手的人看，不要塞進給承辦人的交付說明。
